# Blocks

The `CSharpPython.Blocks` namespace turns a visual node graph into Python source, so a block editor and a text editor share one runtime. The graph is plain serializable data (public fields, lists and strings, so `JsonUtility` or your own serializer can store it), and the compiler checks it as it writes, so a graph that compiles always produces a script the VM accepts.

```csharp
using CSharpPython.Blocks;

var graph = new BlockGraph().AddVariable("hp", "100");

// on_hit(amount): hp -= amount; if hp <= 0: game.explode()
var onHit = new BlockFunction("on_hit", "amount") { Start = "sub" };
onHit.Add(new BlockNode("sub", "change", "hp").Connect("value", "neg").Then("dead"));
onHit.Add(new BlockNode("neg", "neg").Connect("a", "amount"));
onHit.Add(new BlockNode("amount", "get", "amount"));
onHit.Add(new BlockNode("dead", "if").Connect("cond", "low").Then("then", "boom"));
onHit.Add(new BlockNode("low", "le").Connect("a", "hp").Literal("b", "0"));
onHit.Add(new BlockNode("hp", "get", "hp"));
onHit.Add(new BlockNode("boom", "call", "game.explode"));
graph.AddFunction(onHit);

var library = new BlockLibrary().AddFunction("explode", new string[0], module: "game");
BlockCompileResult result = BlockCompiler.Compile(graph, library);

if (result.Succeeded)
    vm.Start(result.Source);                         // ordinary Python: "import game", "def on_hit(amount): ..."
else
    foreach (var d in result.Diagnostics) Highlight(d.NodeId, d.Pin, d.Message);

// At run time, blame the block behind a failed task.
string badBlock = result.Map.Locate(task.Error);
```

- **Execution and values.** Flow blocks (`set`, `change`, `if`, `while`, `repeat`, `for_each`, `for_range`, `break`, `continue`, `return`, `append`, `set_index`, `remove_at`, `set_attr`, `comment`, calls) are chained through execution pins (`next`, `then`, `else`, `body`). `for_range` counts with optional `start`, `stop` and `step` inputs, `get_attr`/`set_attr` read and write a field (the field name is the block's name), and a `comment` block becomes a `#` line in the generated source. Value blocks (`literal`, `get`, arithmetic, comparison, `and/or/not`, `neg`, `index`, `contains`, `is_none`, `choose` (a conditional value), `get_attr`, `list`, pure calls) have no execution pins and are written inline wherever their output is used. A value block that more than one input reads (such as one `add` wired to two `print` blocks) is worked out once per flow step: the first time an input needs it, it is written to a local on the line before that statement (`_b1 = x + 1`) and the other inputs read the local. A variable that changes in between does not change the shared value. Each pass of a loop is a new step, so a value worked out before a loop is worked out again inside it, and a call that can pause the script (a host function described with `latent: true`, or a call to a function in the graph, which may call one) ends the step. A variable read (`get`) and a typed-in value are never shared. A value is not shared where Python only sometimes runs it (the right side of `and`/`or`, the two branches of `choose`), nor in a `while` condition, which runs again on every pass; those are written inline at each use.
- **Typed variables.** A global variable may be declared with a type (`BlockVariable.Type`: `int`, `float`, `bool`, `str`, `list[int]`, a host handle name; empty is `any`). Reading it gives that type, and the `value` pin of `set` and `change` and a loop that stores into it must fit it (an `int` fits a `float` variable). A number, bool or string variable with no starting value starts as `0`, `0.0`, `False` or `""`, cannot start as `None`, and its starting value must be of its type; a list or handle variable starts as `None`. A wildcard (`$T`) or `none` is not a valid variable type. A parameter with the name of a global hides it, so it is untyped. Local variables are not declared and stay `any`. The type is saved as an optional `Type` field (the format version stays 1).
- **Loop variables.** `for_each`, `for_range` and a named `repeat` have one output, the loop's own variable (the item, the count, the pass number), which an input can read by a wire to the loop block (`Connect("arg0", "loop")`). It can only be used by blocks inside the loop's body: wiring it to a block after the loop, before it, or to the loop's own inputs is an error, and so is a value block that reads it and is also read outside the body. `BlockSpec.LoopVariable` tells an editor which blocks have the output, and `BlockTypeChecker.CheckWire` refuses a wire that would leave the body (a block not yet joined to the flow is not judged; the compiler judges it once it is). The output is `int` for `for_range` and `repeat`, and the element type of a list for `for_each`. A `get` block of the loop's name still works anywhere, as in Python, where the variable outlives the loop.
- **Flow joins.** More than one execution wire may enter a block (the `then` and `else` paths of an `if` that both lead to the same block, for instance). Python has no goto, so the flow from the joined block on is written once as a local function, `_join1`, at the top of the function that holds it, and each path ends by calling it. A `return` in the joined part leaves the whole function: the local function answers with a one-item tuple and its callers pass a return on. The flow after the call carries on when the joined part runs to the end (an `if` with its own `next` runs it after the branches and the join). Variables the joined part assigns are declared `nonlocal` (or `global` for a global variable); a variable that only the joined part uses stays local to it, and one it first sets that is also used outside it is an error (set it before the flow splits). Values worked out before the join are not reused inside it. Not allowed: a flow that loops back, `break` or `continue` in the joined part when the join is inside a loop (it is a function of its own), a block entered from inside and from outside a loop, a block entered from different parts of the flow (the root and the joined part of another join), and a joined part that uses the result of a call that did not run on every path into it. A saved task of a script that has a join is tied to the generated code, as for any script.
- **Calls.** A `call` block names a function: a built-in (`print`, `len`, ...), a host function added to the `BlockLibrary` (`game.explode`; the `import` is written for you), or another function in the graph. Arguments are the pins `arg0`, `arg1`, .... A call that is not pure runs in the flow, and a later block may use its result as long as it runs after it, in the same or an enclosing branch. A host function that returns several values (described as `-> (hit: bool, point: Vec)`, see [host API](host-api.md)) has one output per name: wire each from its own output by naming it in the input's `FromPin` (`Connect("arg0", "ray", "hit")`). A call in the flow is unpacked into one local per output (`_b1, _b2 = game.raycast(...)`), and a pure call is indexed where it is used (`math.modf(x)[0]`). Reading a block with several outputs without naming one, or naming one that does not exist, is an error.
- **User-made blocks and events.** Every function in the graph becomes a `def`. A function whose name matches a host event is that event's handler; any function can also be called from other functions, which is how user-made blocks work.
- **Globals.** Graph variables become module-level assignments, and `global` statements are written where functions assign them.
- **Literals.** A typed-in value must be a single number, string, `True`, `False` or `None`, so editor input can never smuggle in code. `BlockLiterals.String(text)` quotes any text safely.
- **Diagnostics.** Unknown blocks or pins, missing inputs, wires whose types do not fit, bad names, flow that loops back, joins that cannot be written (see below), results used before they exist, `break` outside a loop, values that depend on themselves and more are reported against the block and pin at fault. Blocks connected to nothing are warnings.
- **Typed wires.** Every pin has a type, and the compiler reports a wire that does not fit against the block and pin at fault (`BlockTypeChecker.Check` returns the same errors without compiling). `any` fits everywhere, an `int` fits a `float` pin, and every other mismatch is refused: a `str` cannot go to the `count` of `repeat`, and a function's result of type `none` has no value to wire. Built-in blocks have fixed pin types (`repeat` takes an `int`, comparisons give `bool`); host functions get theirs from `Describe` (see [host API](host-api.md)). Some pins are wildcards: `append`, `set_index`, `index` and `choose` tie their pins to one type, taken from the wires (`index` on a `list[int]` gives an `int`, and `append` to it refuses a `str`). An `int` and a `float` make `float`. Operators give `int`, `float`, `str` or a list from their inputs, and `any` otherwise. A `list` block's items need not match (it is `list[any]` then). Variables and `None` are `any`. An editor can ask `BlockTypeChecker.CheckWire(graph, function, toNode, pin, fromNode)` whether a wire may be drawn, and get the reason when it may not, and `OutputType` for the type of a pin.
- **Editing.** `BlockEditor` (`new BlockEditor(graph, library)`) holds the editing rules for any editor, so a canvas never changes the graph itself. Each method checks first and returns an `EditResult` (`Succeeded`, `Reason`, `Node`); a refused edit changes nothing, and the `Changed` event is raised once after each edit that was made. So far: `AddNode(function, block, name, x, y)` (a new id unique across the graph, a place on the canvas, a `call` needs a function the library or graph has, the `Limits` of the editor are kept), `RemoveNode` (takes the block's wires, links, start and editor entries with it), `SetName` and `MoveNode`. Wires and links: `Connect(function, toNode, pin, fromNode, fromPin)` replaces what the pin had and is refused with the reason when the type does not fit (`BlockTypeChecker.CheckWire`), the pin is not one the block has, or the value would depend on itself; `SetLiteral` types a value into a pin; `Disconnect` empties a pin (and forgets the wire's reroute points); `Link(function, fromNode, pin, toNode)` runs one block into another, replacing the pin's old link, and is refused when the target is a value block or the flow would loop back (two paths may meet, which is a join); `Unlink` and `SetStart`. Search (nothing changes): `Search(text, max)` lists the blocks and functions (library and graph) whose title, name or category contain the text, best match first, as `BlockChoice` (`Block`, `Name`, `Title`, `Category`) to pass to `AddNode`; `SuggestForOutput(function, node, outputPin)` and `SuggestForInput(function, node, pin)` are the search for a wire dragged from an output or an input and dropped on empty canvas, using `PinTypeIndex` with blocks, and each choice carries the `Pin` to wire. Functions: `AddFunction(name, parameters...)` (an event handler is a function with the event's name), `RenameFunction` (renames the `call` blocks too), `RemoveFunction` (its blocks go; calls to it stay and compiling reports them as unknown), `AddParameter`, `RemoveParameter` (the callers' pins move up to fill the place) and `RenameParameter` (renames the blocks inside that use it). Global variables: `AddVariable(name, initial, type)`, `RemoveVariable`, `RenameVariable` (renames reads and sets in every function except those with a parameter of that name), `SetVariableType` and `SetVariableInitial`. Names must be valid and unused, types must parse, and the `Limits` are kept. Undo and diagnostics follow.
- **Editor data.** `graph.Editor` (`BlockEditorData`) holds what only an editor needs, in the same file under an optional `Editor` section: block positions and collapsed flags (`Place(id, x, y)`, `LayoutOf(id)`), comment boxes, reroute points of wires (keyed by the block and input pin the wire ends at) and groups of blocks. The compiler never reads it, so the generated Python, its source map and a saved task's fingerprint do not change when a block is moved. A graph with nothing in it is saved without the section, and `Prune(graph)` drops entries for blocks that are gone.
- **Placeholders.** A graph that names a function or block type the host does not have still loads, with the block and its wires kept. `BlockPlaceholders.Find(graph, library)` lists those blocks so an editor can draw them as placeholders, and compiling reports each one ("unknown function 'x' ... a placeholder until the host has it"). The same graph compiles once the function is back.
- **Limits.** `BlockGraph.FromJson(json, limits)` rejects a file that goes over the limits of a `BlockLimits` (the defaults when none is given): the document length, the numbers of functions, blocks (per function and in all), variables, parameters, inputs and links per block, the lengths of ids, names, pin names, comment text, typed-in values and type names, and the sizes of the lists in the editor section. The text length is checked before the file is read. The exception says which limit and the size found, and long names are cut short in it. Set the properties to change a limit; `limits.Problem(graph)` checks a graph built in code. The limits bound the file, not what the graph does when it runs.
- **Saving.** `graph.ToJson()` writes a graph as JSON and `BlockGraph.FromJson(text)` reads it back (a bad document throws `BlockGraphFormatException`). The field names match the public fields, so Unity's `JsonUtility` output reads too, unknown fields are ignored, and a `Version` field guards against newer files.
- **Palette from host modules.** `library.AddModule(vm, "game")` (or `AddAllModules(vm)`, which treats `math` as pure) adds every function of a registered module, with pin names taken from its signature (`ModuleBuilder.Describe`). Parameters with defaults become optional pins: leave them empty and the argument is left out. `library.Palette()` returns the blocks and functions grouped by category and module, ready for an editor's block list.
- **Source map.** `SourceMap.NodeAt(line)` and `LinesOf(nodeId)` link generated lines and blocks, and `Locate(error)` finds the block behind a runtime error. `Running(task)` gives the block a running task is at (null before it starts, after it ends, or on a line no block owns) and `ActiveNodes(task)` lists the blocks it is inside, innermost first: the waiting block, then the call block that entered the function it is in. The task must be running the source the map was made for, and the answer is read on demand, so an editor asks once per frame. Variables can be watched through `task.Globals`.

Not in the first version: loops that wait for a changing call result (a `while` condition cannot use a stored call result; compute it inside the loop and use `if`/`break`), and variadic calls.
