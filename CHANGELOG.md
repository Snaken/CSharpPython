# Changelog

## Unreleased

- New: the benchmarks run on Unity as well as .NET. `benchmarks/configs` has one folder for each way of running them (`dotnet`, `unity-6.3-mono`, `unity-6.3-il2cpp`, `unity-7-il2cpp`); a Unity config builds a small headless player with the Unity CLI and runs it. `python3 benchmarks/run.py` runs every config that can run on the machine, writes `benchmarks/results/*.json`, and draws `docs/performance.svg` and the table in `docs/performance.md` from them. The benchmark scripts moved to `benchmarks/scripts`. Measured in a player, IL2CPP runs the scripts 1.4 to 8.5 times slower than CPython and Mono 5.7 to 18.6 times slower, where .NET is 1.0 to 2.6 times slower.
- Faster: a call to a built-in function or method (`len(x)`, `d.get(k)`, `math.sqrt(x)`) that gives only positional arguments within what the function accepts is made directly by the instruction loop, which saves about 3 ns on each call. Calls with keyword arguments, calls that give the wrong number of arguments (still a `TypeError` with the same text) and `next()`/`send()` on a generator take the same path as before. The `dict_ops` benchmark takes 5.2 ms (CPython: 3.0).
- Faster: reading a member of a module (`math.sqrt`, `random.random`) goes straight to the module's members instead of through the general attribute lookup, which saves about 5 ns on every such read. The `random_math` benchmark takes 12.0 ms (CPython: 11.5).
- Faster: `random.randint`, `random.choice` and `random.shuffle` draw their numbers without a `BigInteger` when the range fits in 31 bits, and every `random` function called with all its arguments by position no longer makes an array to hold them. The numbers drawn for a given seed are the same. The `random_math` benchmark takes 13.5 ms instead of 15.8 (CPython: 11.4).
- Faster: `sorted()` and `list.sort()` of a list of plain ints with no `key` sort one array and write it back, instead of building key, order and result arrays and a second list. The result is the same. The `list_ops` benchmark takes 9.7 ms instead of 11.1 (CPython: 4.9).
- Faster: turning an int or float into text (`str(n)`, `repr(n)`, f-strings, `%s` and a plain `%d`) no longer builds a string builder, a seen-list and a walk scope for each number, and a plain `%d` of an int skips building and parsing a format spec. A 20,000-line string-building script took 2.1 ms instead of 5.2 (CPython: 1.9). Output is the same.
- New: `EditorView.Build(source, vm)` highlights and analyzes a script in one pass and returns the spans with the problems marked on them (`HighlightSpan.Problem` holds the message, and a span is split where a problem starts or ends) together with the diagnostics, so a host no longer merges the two by hand. `Analyzer.Analyze` now parses the tokens it has already made instead of lexing the text again, so it lexes once instead of twice. Measured on a 600-line script, `Build` takes 0.41 ms against 0.52 ms for `Highlight` followed by `Analyze` (0.16 against 0.19 ms for 60 lines). `docs/editor-tooling.md` also says how to draw the spans as Unity rich text (escaping `<`).
- New: `TaskTotals.Of(tasks)` adds up `task.GetDiagnostics()` for any group of tasks: how many, the steps and memory walks, the memory the last walks found (sum and largest), the walk time, and `TasksNearMemoryLimit`, how many tasks are due a walk and so may be stopped by the next slice, which lets a game pause or warn before the library stops a script. It never walks a heap. The VM keeps no list of its tasks, so the host passes the ones it holds.
- New: `task.GetOwner<T>()` returns `task.Owner` as a `T` and throws `InvalidOperationException` (saying whether the owner is missing or of another type) when it is not one, and `task.TryGetOwner<T>(out owner)` returns false instead. `Owner` itself is still an `object` that the host sets, so nothing changes for existing code.
- Faster: a short tuple of numbers, strings and the like (such as a key `(x, y)`) is hashed and compared without the walk budget that guards nested values, about 25% quicker to compare; nested or long tuples and tuples that hold script objects are still budgeted. Results are the same.
- Faster: measuring a task's memory (for `MaxMemoryBytes` and `EstimatedMemoryBytes`) counts a tuple of plain values without entering it in the set of objects already seen, which was most of the cost for a script that keeps many such tuples: a 48 MB task took about 9 ms to measure instead of 28. A plain tuple held in several places is now counted each time, a few bytes too many.
- New: `task.MemoryMeasurements`, `task.LastMeasuredMemoryBytes` and `task.StepsSinceMemoryMeasured` show how often the memory check has walked a task, what the last walk found and how old it is, without walking again. A host can use them to see which script is growing (`EstimatedMemoryBytes` walks the whole heap, so it cannot be shown every frame) and to count how much the `MaxMemoryBytes` check costs. A task far below its limit stays at 0 walks. `EstimatedMemoryBytes` now also records its result as the last measurement. `task.GetDiagnostics()` returns them in one `TaskDiagnostics` value together with the steps run, the memory limit, how many steps remain until the next walk and (only when `VmOptions.CollectDiagnostics` is turned on, off by default) how long the walks have taken in total; reading it never walks the heap.
- **A set or dict keyed by cells such as `(x, y)` takes about an eighth of the memory.** The compact storage now also covers keys that are plain tuples of the same number of integers (two to eight): each key is kept as its numbers in the same `long[]`, with no tuple object, no stored hash (it is the hash `Ops.Hash` gives the same tuple) and nothing for the garbage collector to scan. Measured with a full collection: a set of `(x, y)` tuples 257 to 31.5 bytes a member, a dict keyed by them 289 to 63; adding and looking up such keys in a loop is about 37% faster. A key of another shape (a different length, a float, a string, a `True`, a namedtuple, or a tuple holding any of them) moves the dict back to the ordinary layout, with the same contents and order. The one visible difference: a compact dict makes a new tuple each time a key is read, so the key you get back from iterating is equal to the one you added but is not the same object (`is`). `MaxMemoryBytes` and `EstimatedMemoryBytes` count such a set at 32 bytes a member and such a dict at 64. A snapshot gives the dict key objects while it is written and puts it back afterwards; the format is unchanged.
- **A set of integers takes less than half the memory.** A dict or set whose keys are all integers now keeps them in a plain `long[]` (8 bytes a key, no stored hash, and nothing for the garbage collector to scan, which matters on Unity's Mono and IL2CPP where a collection scans the whole heap). Measured with a full collection: a set of integers 47 to 21 bytes a member, a dict with integer keys 79 to 52 (the values keep their slots). The first key that is not an integer (a string, a float, a `True`) moves the dict back to the ordinary layout, with the same contents and order. A loop that adds to and looks up an integer set or dict is about 10% faster. Results, order, errors and snapshots are the same. `MaxMemoryBytes` and `EstimatedMemoryBytes` count such a set at 24 bytes a member and such a dict at 56, so a script that keeps big integer sets reaches the limit later than before. A set of tuples such as `(x, y)` is unchanged.
- **Less garbage from `a, b = x, y` and from `sorted` of a short list.** Measured as bytes allocated each time the operation runs: `x, y = f(), g()` and the swap `a, b = b, a` 104 to 0 (two or three names on the left and as many values on the right are stored one by one instead of being packed into a tuple and unpacked; the values are still all computed before the first store, left to right, and the stores still go left to right), `sorted(range(4))` 656 to 248 and `sorted(range(4), key=f)` 688 to 400 (a list of up to 16 items whose keys are all integers, all floats or all strings is sorted in place by a stable insertion sort, and a `range` becomes a list of the right size at once). Results and errors are the same. **A saved task of a script that contains such an assignment cannot be restored**, because its compiled code (and so its fingerprint) is different; save again after updating.
- **New blocks for tuples, sets and dictionaries, and a sorted block.** A "Collections" category adds `tuple` ("Tuple of") and `tuple_item` ("Tuple item at"), `set_of` ("Set of"), `set_add` ("Add to set") and `set_discard` ("Remove from set"), `dict_of` ("Dictionary of", with numbered `key0`/`value0` pairs), `dict_get` ("Dictionary item or default"), `dict_set` ("Set dictionary item") and `dict_remove` ("Remove dictionary item"), and `sorted` ("Sorted list", with an optional `reverse`). `contains` ("Is in") now also looks through sets, dictionaries and tuples. A graph can now keep a set of visited cells and take its neighbours nearest first (pair each with its distance in a tuple, sort, read it back), which the block Explorer could not do. `tuple`, `set` and `dict` are plain pin types with no element type, so they can also be declared as variable types; `BlockEditor.PinsOf` offers the next numbered pin for `tuple`, `set_of` and `dict_of` as it does for `list`. Existing graphs are unchanged. See [blocks](docs/blocks.md).
- Docs: [resource limits](docs/resource-limits.md) has a "Moving from 0.2.3" table of the limits that are on by default (what each was, what a script sees when it goes over, what a host does), with the grid size at which a one-list maze hits `MaxSequenceLength` (317 by 317). The documentation of `Describe` now says in both places that a description with no `->` gives one `any` value pin and `-> none` removes it; nothing changed in the code.
- **`BlockEditor.Compile()` keeps its result.** Compiling a big graph is not free (about 35 ms for 10,000 blocks), and a view that compiles after every `Changed` paid it for each block that was only moved. `Compile()` now returns the same `BlockCompileResult` until an edit that could change the program, an undo or redo, or a change to the `BlockLibrary`; moving or collapsing a block and comment boxes, reroute points and groups keep it (`Changed` is still raised for them). New `BlockEditor.ProgramVersion` is a number that changes when the result would, for a view that wants to skip its own work, and `InvalidateCompile()` is for code that changes `Graph` directly, which the editor cannot see. Nothing changes for a host that never calls `Compile()`.
- **A script's `print` can go to one task, and hidden `print` costs almost nothing.** New `task.Output` (an `Action<string>`) receives what that task prints instead of `vm.Output`, so a game can give each game object its own console; it is not saved in a snapshot. New `task.HasOutput` and `CallContext.HasOutput` say whether anyone is listening. With no sink at all, `print` now only checks its keyword arguments and returns: it no longer builds the text (200,000 prints of a few values took 148 ms and now take 43 ms; with a sink they take the same 145 ms). **Behaviour change: with nobody listening, `print` does not run a script's `__str__`**, so a `__str__` that raises or has side effects does not show up until a sink is set; bad keyword arguments are still a `TypeError` either way. See [host API](docs/host-api.md).
- **Block API: the pins of "Is in" are named, and a host can ask which blocks are steps.** **Breaking:** the pins of the `contains` block, `a` and `b`, are now `item` and `collection`, like the other collection blocks. Graphs read with `BlockGraph.FromJson` and graphs given to `new BlockEditor(graph)` are renamed for you (the reroute points of their wires too); `graph.Migrate()` does the same for a graph built in code, which must otherwise use the new names (compiling one with the old names says the pin was renamed). New `BlockLibrary.IsStep(block, callName)` and `BlockEditor.IsStep(function, nodeId)` say whether a block is a step in the execution flow, so a host that lays out graphs in code does not need its own list of flow blocks and pure calls.
- **Block API: the Python a graph compiles to reads better.** An `if` block whose else branch is one more `if` (with nothing after it) is written as `elif`, so a chain of tests no longer steps further right with each one, and a `for_range` block that starts at 0 is written `range(4)`, not `range(0, 4)`. The program does the same; **a saved block task has to be saved again**, because the compiled code and so its fingerprint changed (the same note as for tuples of constants above).
- **Host functions can carry documentation.** `Describe` takes an optional `doc:` text and new `ModuleBuilder.DescribeParameter(function, parameter, text)` gives one parameter a text. Hover shows the doc where a script function shows its docstring, `SignatureHelp` has `Documentation` and a `ParameterDocs` list that parallels `Parameters`, and `CompletionItem` has `Documentation` (its `Detail` stays a one-line signature). `NativeFunction.Doc` and `ParameterDocs` hold the text. Nothing changes for a function without one. For the block editor, `FunctionSpec.Doc` and `ParameterDocs` (one text for each of `Parameters`, in order) are what the palette can show as a tooltip, `BlockLibrary.AddModule` takes them from the host's `Describe`, `AddFunction` takes `doc` and `parameterDocs` for a function added by hand, and `BlockPin.Doc` is the text for an input pin of a call. See [host API](docs/host-api.md).
- **Constants can carry documentation, and hover shows them.** `ModuleBuilder.Constant(name, value, doc)` takes an optional text (`PyModule.DocOf(name)` reads it). Hover on a module constant, written `maze.NORTH` or imported by name, used to show nothing; it now shows `maze.NORTH = 0` with the module as its origin and the text underneath, and a constant with no text still shows its value (`math.pi = 3.14159...`). `CompletionItem.Documentation` is set for constants too. Nothing changes for a constant without text.
- **Snapshots of big lists are about ten times smaller and restore faster (snapshot format version 17).** A list is saved in pieces: a value repeated (`[0] * 90000` takes a few bytes), a block of ints (one or two bytes each, the sign folded in, where every int took nine), a block of bools (one byte each) and a block of any other values. Measured with the Explorer's shape (four lists of 90,601 per-cell entries on a 301 x 301 maze, a dict and a set; one run of `Save` and `Restore` on net10.0): 2,658,327 bytes down to 263,086, `Save` 4.6 to 3.2 ms and allocating 15.8 to 2.2 MB, `Restore` 6.9 to 2.6 ms. **Saves made by version 17 cannot be read by an older library**; version 17 still reads versions 13 to 16, so saves made today still restore (and the fingerprint is unchanged, so no script needs saving again). A damaged snapshot is still refused with `SnapshotException`, repeated values included: a list is only as long as the data or `MaxSequenceLength` allows. Dictionaries, sets and tuples are still saved value by value. See [snapshots](docs/snapshots.md).
- **Block API: a function can be a value, and `sorted` takes a `key`.** New value block `function_ref` ("Function", category "Function values") holds a function of the graph or of the library by name, and the `sorted` block has a new optional `key` pin that takes it: `sorted(items, key=by_distance)`, so a list no longer has to be paired with its keys in tuples (which allocated one per item). Compiling reports a key function that does not take one parameter, an unknown function and a function block with no name. `BlockEditor.AddNode` and `SetName` refuse an unknown function for it, `RenameFunction` renames the blocks too, and `BlockPlaceholders` lists one that names a missing function. A saved graph still loads, since only a block type and an optional pin were added. The output is typed `any`, and a key that pauses the script is not supported. See [Blocks](docs/blocks.md).
- **`PyVm.WarmUp()` and `BlockEditor.WarmUp()` take the first-tick cost out of the game.** Where the runtime compiles code as it is first used (desktop .NET, Mono, the Unity editor), the first script in a process cost about 13 ms to compile and 11 ms for its first `Update` whatever it was, which showed up as a 12 to 14 ms first tick for 192 racers (the work per racer is small: 1.3 ms for all 192 once warm). `PyVm.WarmUp()` runs a representative script, with a save and restore, on a private VM (about 50 ms once, under 1 ms after) and the first compile and first tick fall to 0.2 and 1.4 ms; `BlockEditor.WarmUp()` does the same for block compiling and editing (about 25 ms; 28 ms of first use fall to 0.4 ms). Call them while loading. They touch no VM, graph or editor of yours, never throw, and can be called any number of times from any thread. Little to gain under IL2CPP. See [performance](docs/performance.md).

## 0.2.4

Security hardening and limits, faster and smaller collections, and what the examples needed from Blocks. **Read the breaking notes before updating.** The snapshot format is still version 16, but **a saved task of a script that contains a tuple of constants such as `(0, 1)` cannot be restored**, because that tuple is now built once when the script is compiled and the compiled code (and so its fingerprint) is different. The new defaults also change what scripts may do: `MaxSequenceLength` 100,000, `MaxMemoryBytes` 64 MB, `MaxSourceLength` 1,000,000 characters, and a `HostError` now only names the .NET exception type (the exception itself is `task.Error.InnerException`). A host that needs more raises the limits in `VmOptions`.

- **Less garbage from everyday operations.** Measured as bytes allocated each time an operation runs (a call, an attribute or method access, `try` and a native call such as `abs` already allocated nothing): `a, b = t` of a tuple or list 104 to 0, `min(a, b)` and `max(a, b)` 336 to 0, a tuple of constants such as `(1, 2)` or `(0, -1)` 104 to 0 (it is built once when the script is compiled and shared, as in CPython, so `(1, 2) is (1, 2)` is `True`), `for i, x in enumerate(xs)` over three items 688 to 64 (the pair goes straight to the two names), and `sorted` of five items 1,016 to 667 (and with a `key` 856 to 600). A script that loops over many such operations makes fewer garbage collections.
- Fixed: `xs.sort(key=f)` where `f` (or a comparison) changed `xs` ended the task with a `HostError` (`ArgumentOutOfRangeException`). The sort now works on a copy and raises `ValueError: list modified during sort` if the list changed, as CPython does.
- **A dict or set takes about half the memory, and a set no longer stores values.** `PyDict` keeps keys, values and hashes in arrays with its own compact table of positions (like CPython's dict), instead of a .NET `Dictionary` beside an array of entries. Measured on 200,000 entries with a full collection: a set of integers went from 145 to 47 bytes a member, a dict of integers from 145 to 79, a dict of strings from 218 to 115 and a set of two-item tuples from 249 to 151. A set (and any dict that only holds `None`) has no value array at all. Lookups and inserts are as fast or faster (a dict of string keys 33% faster, the others within noise). Insertion order, iteration, snapshots and the rules for keys are unchanged, and a key's `__eq__` that changes the dictionary no longer upsets a lookup.
- **The memory estimate now matches the real size.** `MaxMemoryBytes` and `EstimatedMemoryBytes` counted a set member as 48 bytes when it cost 145, and an empty list, tuple or dict at much less than its real size. They now use 80 + 24 bytes an item for a list, 56 + 24 for a tuple, 112 + 80 an entry for a dict and 112 + 48 for a set. **A script that keeps many small lists, tuples or dicts reaches `MaxMemoryBytes` sooner than before, because the old numbers were too low.**
- A runtime error shows how it got there. `FormatTraceback()` now prints the line of the script under each call, as CPython does (`Script.Source` and `Script.SourceLine(n)` keep the text, also for a restored task), and a call that repeats, as in a deep recursion, is shown three times and then counted (`[Previous line repeated 94 more times]`). `PyRuntimeError.ToString()` is the whole traceback (for a `HostError` it ends with the .NET exception that caused it), so logging `task.Error` is enough; `Message` stays the short form. An error raised outside the interpreter loop (a `HostError` or `MemoryLimitExceeded` from the final safety net) carries the call stack too. `SourceMap.Path(error)` lists the blocks on the path to an error, innermost first. [Host API](docs/host-api.md) has a new "Reading an error" section. **A host that compared `FormatTraceback()` or `ToString()` of an error with a fixed text must update it.** Each `Script` now holds its source text.
- Blocks: two list blocks. `pop` ("Remove and return item") removes the last item of a list, or the one at an optional `index`, and its value can be wired to later blocks (a step in the flow with an output, written `_b1 = xs.pop()`). `list_of_size` ("List of size") is `[value] * count`, so a graph can make a list of 90,601 zeros in one step instead of a loop of appends. Both are typed (`list[T]` to `T`, and `T` to `list[T]`) and appear in `Search` and the wire searches. `BlockSpec.FlowValue` is true for `pop`.
- Docs: [resource limits](docs/resource-limits.md) says plainly that a script which remembers every value it has seen grows without bound, what that does to garbage collection pauses, and how to bound it (`MaxMemoryBytes`, `EstimatedMemoryBytes`, scripts that forget).
- Blocks: `BlockEditor.Search`, `SuggestForOutput` and `SuggestForInput` offer the graph's variables: `Get score`, `Set score` and `Change score` (the variable in `BlockChoice.Name`) instead of the generic Get, Set and Change entries that had no variable, and a wire search offers only the ones whose type fits. `BlockChoice` has a public constructor. **A host that listed the generic Get, Set and Change choices must now use `Name` as the variable.**
- Blocks: a host module can mix actions and questions. `Describe(name, signature, pure: true)` marks one function as pure, and `BlockLibrary.AddModule(vm, module, pureFunctions)` marks the ones it names, so a question such as `maze.wall_ahead` is a value block (it can be the condition of a `while`) while `maze.forward` stays a step in the flow. Before, `AddModule(..., pure: true)` was all or nothing.
- Faster: `any`, `all`, `sum`, `list`, `tuple`, `sorted` and the other built-ins that build a list take a generator's values in one run of the interpreter, instead of resuming the generator once for each value. `any` and `all` over a generator expression take about 25 ns an item instead of 70, and `sum` about 17 instead of 52; the `builtins_stream` benchmark went from 162 ms to 61 ms. Generators still stop where the built-in stops (`any` leaves the generator after the value it found), and an error raised while adding or collecting values reaches the script from the built-in, not from inside the generator. One difference: while the built-in works, the generator counts as running, so script code it calls (an `__add__` in `sum`) that touches the same generator gets `ValueError: generator already executing`.
- The benchmarks raise `MaxSequenceLength` to one million, because `strings.py` joins a 340,000-character string and the default of 100,000 now stops it. The table in `docs/performance.md` is measured again: every script runs from as fast as CPython to 2.8 times slower.
- **Security: strings are hashed by the library, with the process seed.** The string hash relied on `string.GetHashCode()`, which is randomized on .NET Core but not on every runtime (Unity's Mono and IL2CPP may use a fixed one), so a script could find colliding strings offline and make dict and set inserts quadratic. `hash("a")` now differs from run to run on every runtime.
- Fixed `math.isqrt` of an integer over about 1000 digits, which ended the script with a `HostError` (an `OverflowException` from a floating-point estimate).
- The registry of exception types is capped at 4,096 names, so crafted snapshots cannot grow it without limit; `docs/host-api.md` has a new Threads section.
- **Security: running out of memory no longer reaches the host.** An `OutOfMemoryException` used to be rethrown out of `PyTask.Run`/`Update` (and out of `Restore`), so a gap in the memory limits ended the whole game. The task now fails with an uncatchable `MemoryLimitExceeded` (the exception is `task.Error.InnerException`), its stack is cleared, and `Restore` reports a `SnapshotException`. `Run` also has a final safety net, so work outside the interpreter loop (starting an event handler, measuring memory) fails the task too. The host should drop a task that failed this way.
- **Security: a value that holds the same child twice at every level can no longer hang the game.** `a = (a, a)` forty times has about 2^40 paths, and `hash(a)`, `a == b`, `a < b`, `str(a)` and using it as a dict key or set member walked every one inside a single native call, past `MaxSteps`. Each hash, comparison and repr now counts the containers it visits (charged as steps) and ends with a catchable `RecursionError` past eight times `MaxSequenceLength`; `str` and `repr` also stop with `MemoryError` past sixteen times `MaxSequenceLength` characters. See [resource limits](docs/resource-limits.md).
- **Security: `str.replace(old, new, count)` checks the result size before building it.** With a count it skipped the `MaxSequenceLength` check, so a 100,000-character string could be replaced into millions of characters and the result passed on to the next call.
- **Security: `VmOptions.MaxSourceLength`, one million characters by default.** `PyVm.Compile` (and `Start(string)`) throws a `PySyntaxError` for longer text before parsing it, because compiling a 50 MB literal took over 600 MB. 0 turns the limit off, any positive size may be set and a negative one throws from the `PyVm` constructor. **A host that compiles a script of more than a million characters has to raise it.**
- **Security: `VmOptions.SnapshotKey` signs snapshots.** With a key (at least 16 bytes), `PyTask.Save` writes an HMAC-SHA256 signature in front of the snapshot and `PyVm.Restore` throws `SnapshotException` for data that was not signed with that key or was changed, which stops an edited save from resetting the step budget or forging handles. Without a key nothing changes; a signed snapshot cannot be restored without the key and the other way round. [Snapshots](docs/snapshots.md) now says plainly that a snapshot is untrusted input unless protected, and what an edited one can do.
- **Security: a script error raised inside a sort comparison now reaches the script, and .NET exception text no longer leaks.** `sorted` and `list.sort` ran on .NET's own sort, which wraps whatever the comparison throws, so a `RecursionError` (or any error) raised by a script's `__lt__` or key function inside a sort came out as an uncatchable `HostError: Failed to compare two elements in the array`. `sorted` and `list.sort` now use their own stable merge sort, which calls only `__lt__` as Python does (it used to call it twice per comparison, so a class that counts its `__lt__` calls sees fewer), and an error raised inside a sort is the script's error. A `HostError` (a host function that throws something other than `PyError`) now has the `Problem` `an internal error stopped the script (InvalidOperationException)`, naming only the .NET type; the exception and its message are `task.Error.InnerException`. **A host that showed `task.Error.Problem` for a `HostError` now has to read `InnerException` for the details.**
- **Security: deeply nested calls from native code into script code (a sort inside a comparison, a getter inside a getter) can no longer overflow the stack.** Each level nests a whole interpreter loop on the .NET stack, and .NET needs room on top of that to throw an error up through every level, so on a 1 MB stack the 40 levels the VM allows could end the process. A call from native code now checks that there is room (about 64 KB, and 12 KB more for each level of nesting) and raises `RecursionError` when there is not.
- **Security: a script can no longer build an endless exception chain.** Raising inside an `except` block makes the new exception remember the one being handled (`__context__`) and every exception also keeps the call stack it was raised from, so a script that kept raising there used about 900 bytes a step (4.5 GB at the default `MaxSteps`). The chain is now cut after 64 links (the first 64 `__context__` links are kept; `__cause__` is not touched), and the traceback of an exception counts towards `MaxMemoryBytes` and towards the bound that decides when memory is measured. Chains of up to 64 exceptions behave as before.
- **Security: a script can no longer flood a dict or set with keys that share a hash.** Integer keys like `(a << 32) | a` all hashed to 0, so 40,000 inserts took 6 seconds (120 times slower than ordinary keys) and the cost grew with the square of the key count; tuples such as `(k, C - 31 * k)` and sets such as `{k, N - k}` collided the same way. Integers beyond 32 bits, floats with a fraction, big integers, tuples, frozensets, slices and ranges are now hashed with a mixer that uses a seed chosen when the process starts, as strings already were. Equal values still hash alike (`1`, `1.0` and `True`; an integer and the float with the same value). Integers that fit in 32 bits are still their own hash, so `hash(5)` is `5`. **`hash()` of a larger integer, a fractional float, a tuple and so on now differs between runs of the program**, as it does for strings.
- **Security: `VmOptions.MaxMemoryBytes`, 64 MB by default.** Limits the memory one task can reach, so a script that keeps many large objects (each within `MaxSequenceLength`) can no longer use gigabytes. It is an estimate of what the task holds (its globals, stack and everything reachable from them, each object once), checked as the task runs, so it is soft: a script may pass it a little before it is stopped. Going over ends the task with an uncatchable `MemoryLimitExceeded` error, like `StepLimitExceeded`. 0 turns it off and any positive size may be set. `PyTask.EstimatedMemoryBytes` returns the estimate. A task that holds most of its limit runs slower while it is checked (65 to 80% in a measured worst case); see [resource limits](docs/resource-limits.md). **A script that keeps more than 64 MB now stops unless the host raises the limit.**
- **Security: `VmOptions.MaxSequenceLength`, 100,000 by default.** The most items one string, list, tuple, dict, set or deque can hold, and the widest format field. A host can raise it up to 4,194,304; a value outside 1 to 4,194,304 throws `ArgumentOutOfRangeException` from the `PyVm` constructor. Dict and set stores, `update`, `setdefault`, `add`, `union`, deque methods, `list.insert` and slice assignment were not limited before at all (only `append`, `extend`, `+`, `*` and similar were, at a fixed 4,194,304), so a script could grow them without bound; now going over raises a catchable `MemoryError`. **Scripts that build a collection of more than 100,000 items now fail with `MemoryError` unless the host raises the limit.** See [resource limits](docs/resource-limits.md).
- **Security: native work on large values now costs steps.** `x in big_list`, `sorted`, slicing, `+` and `*` on sequences, `==` of sequences, `str` methods and the list, dict, set and deque methods that walk a value were one step however big the value was, so `StepsPerSlice` did not bound a frame and `MaxSteps` did not bound running time (one `in` on a 4 million item list took 25 ms, and a loop of them minutes). They are now charged 1 step for every 16 items (sorting `n log n`) before the work is done, and a charged call ends the slice. A script that is not near its step limit is not affected, but one that scans big lists in a loop now stops at `MaxSteps`. See [resource limits](docs/resource-limits.md).
- **Security: a script can no longer crash the host with deep nesting.** Hashing deeply nested tuples or frozensets, and calling iterators (`map`, `zip`, `filter`, `enumerate`, `itertools`) or `functools` objects (`partial`, `lru_cache`) built on one another 100,000 deep, overflowed the stack, which ends the whole process. They now raise a `RecursionError` the script can catch. Saving a snapshot of a value nested too deeply raises `SnapshotException` instead of overflowing, and restoring was already safe.
- `BlockEditor.SetLiteral` refuses a typed-in value whose type does not fit the pin (a number into a text pin, a text onto a list of numbers), and text that is not a single number, string, `True`, `False` or `None`, with the reason. `BlockTypeChecker.CheckLiteral` answers the same question without changing the graph.
- The operator blocks refuse two typed inputs that Python cannot combine, such as text minus a number, a number compared with a text, or a number as the container of "is in". The compiler reports it, and `Connect` and `SetLiteral` refuse the edit with the reason. Pins of unknown type (`any`, `None`, variables, nothing wired) are never refused, and equality and logic take anything. **Block graphs that wire such a pair no longer compile.**
- `BlockEditor.PinsOf(function, node)` lists the pins of a block for a canvas to draw (`BlockPin`: name, kind and type), so it does not have to work them out from the library itself.
- `BlockEditor.SuggestForOutput` and `SuggestForInput` also offer the functions of the graph.

## 0.2.3

The node view groundwork: typed pins, a type-checked and more capable Blocks compiler, the editing rules an editor needs (`BlockEditor`), and the current line of a running task. The language and the VM are unchanged, and the snapshot format is still version 16. **A saved task of a block script in which one value block feeds several inputs cannot be restored**, because the generated script is different (see the shared value entry), and **block graphs that wire a value of the wrong type no longer compile**.

- Host functions can declare types: `Describe("spawn", "kind: str, count: int = 1 -> Entity")`, with several named results as `-> (hit: bool, point: Vec)`, and `latent: true` for a function that can pause the script. Types are `any`, `int`, `float`, `bool`, `str`, `none`, `list[T]` and host handle names. Untyped descriptions work as before and signature help still shows the plain parameter list. This is the first step of the [node view](docs/node-view-design.md).
- The built-in functions and the `math` and `random` modules have types (`HostSignature` on `NativeFunction.Typed` for host functions; the built-ins are described by an internal table).
- `PinCompatibility.Check(from, to)` says whether an output of one type may be wired to an input of another, with the reason when it may not: `any` fits on either side, `int` fits `float`, lists need the same element type, and every other mismatch is refused.
- `BlockLibrary` functions carry pin types (`FunctionSpec.ParameterTypes` and `Outputs`) from the typed descriptions, and `PinTypeIndex` finds the functions that fit a pin: `Accepting(type)` lists the inputs an output may be wired to, and `Producing(type)` lists the outputs that fit an input.
- Blocks are type-checked. Every built-in block has pin types (`BlockSpec.InputType` and `OutputType`), with wildcard pins written `$T` that take their type from the wires (`index`, `append`, `set_index` and `choose`), and the compiler reports a wire that does not fit against its block and pin. **Block graphs that wire a value of the wrong type (a string into a `repeat` count, a string appended to a list of numbers) no longer compile.** `BlockTypeChecker` checks a graph, gives the type of a block's value, and says whether a wire may be drawn (`CheckWire`) with the reason when it may not.
- Pin types of `print` and other built-ins that were registered with their own pin names are matched to the parameter they stand for, not by position.
- A block can have several outputs. A host function described as `-> (hit: bool, point: Vec)` gives one output per name, and an input picks one with the new `BlockInput.FromPin` (`Connect("arg0", "ray", "hit")`). A call in the flow is unpacked into one local per output, and a pure call is indexed where it is used. Each output is type-checked on its own, and `BlockTypeChecker.OutputType` and `CheckWire` take an optional output name. Saved graphs gain an optional `FromPin` field; older files load unchanged.
- A value block that several inputs read is worked out once per flow step: the first time an input needs it, it is written to a local on the line before that statement (`_b1 = x + 1`) and reused. A loop pass starts a new step, and so does a call that can pause the script (`Describe(..., latent: true)` on a host function, or a call to a function in the graph). Variable reads and typed-in values are not shared, and a value is not worked out early where Python only sometimes runs it (the right side of `and`/`or`, the branches of `choose`, a `while` condition). `FunctionSpec.Latent` and `BlockLibrary.AddFunction(latent:)` carry the flag. **A saved task of a block script in which one value block feeds several inputs cannot be restored after this change**, because the generated script, and so its fingerprint, is different.
- Flow joins: more than one execution wire may enter a block. The flow from that block on is written once as a local function (`_join1`) and each path calls it; a `return` in it leaves the function, and variables it assigns are declared `nonlocal` or `global`. The old error "flow cannot loop back or join up again" now only reports a loop back. `_join1`, `_join2`, ... are reserved names, like `_b1`. Reported as errors: `break` or `continue` after a join inside a loop, a join entered from inside and outside a loop or from different parts of the flow, a result that did not run on every path into the join, and a variable first set after a join that is also used outside it.
- Loop blocks have an output: `for_each`, `for_range` and a named `repeat` give their item, count or pass number to an input wired to the loop block. It can only be used inside the loop's body; the compiler reports any other use, and `BlockTypeChecker.CheckWire` refuses the wire for an editor (`BlockSpec.LoopVariable` marks the blocks that have it). `BlockTypeChecker.OutputType` types it (`int`, or the element type of the list).
- Global block variables can be declared with a type (`BlockVariable.Type`, `AddVariable(name, initial, type)`, saved as an optional `Type` in the JSON). Reading one gives its type, `set`, `change` and loops that store into it are checked against it, a number, bool or string variable starts as `0`, `0.0`, `False` or `""` when no starting value is given, and a starting value of the wrong type is an error.
- Block graphs keep editor-only data in the same file: `BlockGraph.Editor` holds block positions, collapsed flags, comment boxes, reroute points and groups, saved as an optional `Editor` section (format version still 1). The compiler ignores it, so moving a block never changes the generated program or invalidates a saved task.
- `BlockPlaceholders.Find(graph, library)` lists the blocks that name a function or block type the host does not have, so an editor can show them as placeholders; the graph still loads and keeps their wires, and the compile error now says the block is a placeholder.
- `BlockGraph.FromJson(json, limits)` checks a file against `BlockLimits` (document length, counts of functions, blocks, variables and links, lengths of ids, names, values and types, and the editor section) and rejects one that goes over, saying which limit. The defaults are generous for hand-made graphs, and a host can change them. `BlockLimits.Problem(graph)` checks a graph built in code.
- `new PinTypeIndex(library, includeBlocks: true)` also searches the built-in blocks: a block's input pins accept an output, and its output (a loop block's variable included) is found by the type an input needs. A wildcard pin (`$T`) fits any type. `PinMatch.Block` is set for these and `PinMatch.Function` is then null. Without the flag the results are the same as before.
- `PyTask.CurrentLine` and `PyTask.GetCallStack()` say where a task is, for an editor to highlight the running line (a waiting task is on the line of the call that waits; 0 once it has finished or failed). Reading them costs nothing while the task runs, and a restored task reports the same lines.
- `SourceMap.Running(task)` and `SourceMap.ActiveNodes(task)` map a running task to the block it is at and the blocks that called into it.
- `BlockCompileResult.DiagnosticsOf(nodeId)` gives the diagnostics for one block, errors first.
- `BlockEditor` holds the host-independent editing rules for a block graph: `AddNode`, `RemoveNode`, `SetName`, `MoveNode`, `Connect`, `SetLiteral`, `Disconnect`, `Link`, `Unlink` and `SetStart`, `Search` by text and `SuggestForOutput`/`SuggestForInput` by pin type (returning `BlockChoice`), `AddFunction`, `RenameFunction`, `RemoveFunction`, `AddParameter`, `RemoveParameter`, `RenameParameter`, `AddVariable`, `RemoveVariable`, `RenameVariable`, `SetVariableType` and `SetVariableInitial` (renames update the blocks that use the name), and `Undo`/`Redo` with `BeginGroup`/`EndGroup` to make a drag or compound action one step, `Compile()` and `Placeholders()`, and the layout edits (`SetCollapsed`, comment boxes, reroute points and groups, all undoable), each returning an `EditResult` with the reason when refused, a `Changed` event after each edit, and `Limits` that stop the graph growing past them.

## 0.2.2

The first standard library modules beyond 0.2.0 (`itertools`, `functools`, `operator`), `match` statements and exception chaining. **Saved tasks from 0.2.1 or earlier of a script with a `try` statement cannot be restored** (see the exception chaining entry), and the snapshot format is now version 16, which still reads versions 13 to 15.

- `functools.cmp_to_key` and `total_ordering`, and `itertools.tee`.
- `int(x, base=2)` takes the base as a keyword.
- Error messages follow CPython 3.14: every division or modulo by zero says `division by zero` (and `0 ** -1` says `zero to a negative power`), and a variable used before it has a value says `cannot access local variable 'x' where it is not associated with a value` (for a variable of an enclosing function, `cannot access free variable 'x' where it is not associated with a value in enclosing scope`).

An error raised while an `except` block handles another one remembers it as its context, including errors the VM raises and ones raised by a function that the block calls. - `match` statements: literal, capture, wildcard, value, sequence (with `*rest`), mapping (with `**rest`), class, `|` and `as` patterns, and guards. `match` and `case` stay ordinary names anywhere else. The editor tooling highlights them as keywords where they start a block.

They are lazy, and snapshots save them in the middle of a loop (snapshot format version 15, which still reads version 13 and 14 saves).
- `functools.reduce`, `partial`, `lru_cache`, `cache` and `wraps`, and an `operator` module with the arithmetic, bitwise, comparison and truth functions, `itemgetter`, `attrgetter` and `methodcaller`. A cached function that is called while a snapshot is taken is saved with its cache (snapshot format version 15, which still reads version 13 and 14 saves).

## 0.2.1

A speed release: no language changes, and saved tasks from 0.2.0 still restore (the snapshot format is still version 13).

- Faster: small dictionaries and object attributes are searched in place instead of through a hash table (creating an object and setting attributes take about 40% less time), `sort`/`sorted` of ints, floats and strings, `sum` over ints, list and set comprehensions, calls of list, str, deque and dict methods, `str.split` on one character, and f-strings.
- Faster: the interpreter combines common runs of instructions (a local with a constant, a comparison with its jump, arithmetic on a local), calls script functions without the general argument binding, reads and sets instance attributes directly, and keeps the less common instructions out of its main loop so that each call from native code into a script costs less. `fib(24)` takes 4.8 ms instead of 6.9 ms.
- Faster: a small function that only does arithmetic, comparisons and reads (`key=lambda x: -x`, `lambda p: p.hp`) runs without a frame when `sorted`, `min`, `max`, `map` or `filter` call it, and generators no longer allocate on every `yield`. `min(range(10**6), key=lambda x: -x)` is 4 times quicker.
- Measured against CPython, every benchmark script runs 1.3 to 2.8 times slower than it, where before it was up to 5 times. (`benchmarks/` now warms up for a second before timing.)
